# Engineering Walkthrough

**Project:** Recruitment Scam Investigation and Campaign Intelligence Platform
**Documentation date:** 23 October 2026
**Status:** Active implementation. This document describes code that exists, decisions made, checks actually run, and work that remains. It is not a production-readiness claim.

## 1. Product boundary and operating principle

The application is a case investigation workspace. It collects user-submitted recruitment material, extracts candidate facts and identifiers, checks exact identifiers against a configured local evidence corpus, and connects cases through deterministic matching rules. Investigators review extracted entities and evidence before stronger machine assessments are available.

The platform never labels a person a scammer. It separates:

1. **Observed submission content:** text or OCR-derived text and the original uploaded item.
2. **Extracted candidates:** machine-found identifiers and labeled claims. Confidence describes parser certainty, not truth.
3. **Source records:** what a configured source returned, including its source reference, outcome, excerpt, authority category, and retrieval time.
4. **Machine findings:** versioned rules applied to investigator-confirmed candidates and reviewed evidence.
5. **Human dispositions:** separate investigator records, with stronger dispositions requiring an independent reviewer.

An empty local search is scoped to that corpus and is never treated as proof of fraud or legitimacy. Campaign scores are deterministic investigative signals, not probabilities or guilt findings.

## 2. Architecture selected for this repository

The repository began without an application implementation. The delivered structure uses:

| Component | Role | Authoritative data |
|---|---|---|
| React, TypeScript, Vite | Intake, case review, timeline, graph, campaigns, source corpus, corrections, human review, findings and reports | No; UI state is fetched from the API |
| FastAPI | Authentication, permissions, validation, case and review APIs, report serialization, health response | No; commits to PostgreSQL |
| PostgreSQL | Users, cases, consent, uploads metadata, entities, evidence, source corpus, findings, campaign links, dispositions, corrections, audit events and durable jobs | Yes; the system of record |
| Alembic | Ordered, repeatable schema migrations | Schema history |
| Worker process | Claims durable processing jobs and graph projection outbox events; parses text/PDF/image material, extracts candidates, queries the local corpus and (only when configured and separately consented) RDAP, persists evidence/findings, and retries graph projection updates | PostgreSQL |
| Neo4j | Rebuildable projection of case/entity/campaign relationships | No; it can be rebuilt from PostgreSQL |
| Private upload volume | Original PDFs and images under opaque server-generated filenames | Upload metadata and retention decisions remain in PostgreSQL |
| Nginx | Serves the compiled frontend, applies browser security headers, and proxies same-origin `/api` requests to FastAPI | No |

Docker Compose describes PostgreSQL, Neo4j, API, worker and frontend services. A Compose configuration parse has passed; a live Docker deployment has not been validated because the Docker Desktop Linux engine was unavailable in the environment.

PostgreSQL is enforced at API and worker startup; SQLite is permitted only with `APP_ENV=testing` for test harnesses. The current version baseline is Python 3.12 with pinned packages in `backend/requirements.txt`, Node.js 22 and pnpm 11.25.0 with a frozen frontend lockfile, PostgreSQL 16.15 Alpine, Neo4j Community 2026.10.2, Nginx 1.30.6 Alpine, and Caddy 2.11.9 Alpine. The PostgreSQL image is built from the official image, refreshes Alpine security packages, uses Alpine `su-exec` through the upstream entrypoint's `gosu` command name, and copies the patched merged filesystem into a fresh final image so obsolete upstream layer binaries are not retained. The dependency-free redaction tests require Node.js 22.6 or newer for built-in TypeScript stripping. The container image tags allow upstream patch updates; production operators should pin reviewed image digests. These are configured compatibility targets; local checks are recorded in the dated implementation checkpoints.

## 3. Full case workflow, step by step

### 3.1 Intake and consent

1. A user registers and signs in. The initial investigator uses a one-time bootstrap code; a separate reviewer setup code provisions a different role. A seeded singleton database gate serializes these registrations so concurrent attempts cannot both claim the first privileged role. Other accounts receive analyst access. The current deployment is a shared single workspace, not a multi-tenant service: analysts can see all cases in redacted form, and investigators/reviewers can inspect submitted source material. Reviewer-only account and disposition-review operations use separate role checks.
2. The user enters a text, URL, email/message, or uploads a PDF or image. The intake UI presents the current consent version and retention period. For pasted text, the submitter can select a span and replace it with `[REDACTED BY SUBMITTER]` before submission; the UI warns that the removed content will not be available for extraction. Image/PDF files must be redacted in an appropriate local editor before upload.
3. The API requires explicit consent and rejects stale consent versions. It validates titles, MIME types, upload size and file signatures. An outer ASGI guard rejects all write bodies before parsing: API `POST`/`PATCH`/`PUT` requests default to 128 KiB; upload bodies allow `MAX_UPLOAD_BYTES + 64 KiB` for multipart metadata; text-case JSON allows 512 KiB for the 100,000-character schema maximum. It checks declared length and counts streaming chunks.
4. Uploads receive opaque randomized names and are AES-256-GCM encrypted before exclusive creation in a private volume; a fresh random 96-bit nonce is used per file and the version plus filename are authenticated as associated data. API and worker require a canonical base64 32-byte key outside `APP_ENV=testing`, and they fail closed on key, tag, filename, or format mismatch. On POSIX, API startup and worker retention enforce directory mode `0700`; file creation sets mode `0600`. On Windows, inherited ACLs must restrict the mounted directory to the service identity and authorized administrators. No public upload URLs are created.
5. PostgreSQL stores the case, consent version/time, submission metadata, initial evidence record and a durable processing job. The UI can show queued, processing, completed or failed states.

### 3.2 Background extraction and source checks

1. The worker claims a persisted job and marks the case as processing.
2. Text is parsed directly. PDFs are processed page by page; when a page has no embedded text, OCR is attempted. Images use local OCR. Limits are applied to file size, PDF pages, image pixels and OCR duration.
3. Deterministic parsers extract email, Indian phone, URL/domain, UPI-shaped values, IFSC-shaped codes, bank account numbers only after an explicit account label, and fee-request wording. Explicitly labeled company, role, recruiter and location claims, two constrained hiring phrases for company/role, literal date shapes and INR/₹/Rs amounts are also captured. Narrative company/role candidates have lower parser confidence, exact spans and explicit uncertainty. Bank accounts are sensitive and masked in graph/report displays; IFSC codes are excluded from campaign linking because they identify shared bank branches, not individual accounts.
4. Each candidate keeps its original and normalized value, source location, exact text offsets where available, parser method, extraction confidence and an uncertainty explanation. OCR now retains Tesseract word boxes and maps matched identifier spans to a compact `*_ocrpx_x_y_width_height` source location (PDF coordinates are from the 2x OCR render; image coordinates are in source-image pixels). Text-native PDF pages keep page-relative spans without a region box. Case and campaign views format these stored boxes into readable labels.
5. The local evidence adapter performs exact normalized identifier matching. A hit stores source and retrieval metadata; a miss stores an explicit neutral `no_result`. The local corpus is initially empty and must be populated with material the operator can lawfully retain and cite.
6. The worker persists evidence, recomputes the current machine findings and records an audit event. A failure is captured on the job and retried up to the configured implementation limit; exhausted work is marked failed.

### 3.3 Investigator review and findings

1. An investigator opens a case and can inspect the source excerpt, location, extracted candidates, evidence outcomes, source references, retrieval times, timeline, and campaign links.
2. Candidate entities can be confirmed or rejected. Evidence can be marked relevant, irrelevant, left for review, or marked as contradicting the claim; a rationale is recorded.
3. The current findings rules live in `backend/app/findings.py` as `exact-source-evidence-v1`. The rules require an investigator-confirmed entity before assigning a stronger source-based assessment.
4. “Confirmed by an authoritative source” requires a result-bearing source entry whose category and authority agree, which an investigator marked relevant, and which has a source reference and excerpt. The finding describes only the source-record claim and exact identifier match; it does not determine wrongdoing.
5. “Evidence supports concern” is limited to an investigator-reviewed source-labeled unverified public report. The system explicitly calls it an allegation or report.
6. “No adverse evidence found” is restricted to confirmed matchable identifiers for which every linked source result is a local-corpus `no_result`. It does not mean the identifier is safe or legitimate.
7. Failed, unavailable, unchecked, unreviewed or irrelevant results cannot produce a negative or adverse decision. An investigator-marked contradiction blocks a stronger case summary; the system does not resolve conflicting source statements.
8. Every recomputation supersedes, rather than overwrites, prior findings. Findings retain their rule version, supporting/conflicting/unreviewed evidence IDs and an evidence snapshot with source reference, outcome and retrieval timestamp.
9. Case-level human dispositions remain separate. Stronger dispositions require relevant result-bearing evidence and a second reviewer; the proposer cannot review their own disposition.

### 3.4 Cross-case links and campaign groups

1. Investigators trigger deterministic link recomputation from normalized exact identifiers.
2. Phone, email, UPI and exact bank-account matches contribute 40 points; URL contributes 25; domain contributes 15. IFSC codes are not campaign keys. A URL and its derived host count once. Scores cap at 100 and are not probabilities.
3. The threshold is configurable through `CAMPAIGN_LINK_THRESHOLD`; it is embedded in the rule version. Previous versions remain available for historical inspection.
4. The API and UI explain matched identifiers, the rule and score, evidence references, case membership and review state. Rejected identifiers are excluded; links are staled when their supporting match disappears and can be reactivated after recomputation.
5. Neo4j is an optional projection. Case changes and coalesced graph outbox events are committed together in PostgreSQL; the worker retries projection failures with backoff and recovers abandoned running work after a timeout. A generation counter prevents older in-flight updates from completing over newer case changes. Delete tombstones survive case-row deletion, and unused identifier nodes are pruned. The API derives graph data from PostgreSQL while Neo4j is unavailable or any projection event is pending, so it does not serve a known-stale graph. Entity handles are hashed and identifier labels are masked. Evidence nodes store only source category, minimized source reference, outcome, authority, retrieval time and review status; free-text source names, claims, excerpts, rationales and case titles are excluded and old graph properties are removed on synchronization. The investigator graph supports entity/source/date/review filters, shows case/evidence/entity and campaign relationships, and links a selected case or evidence node to its access-controlled case view for detailed source inspection. Graph link explanations preserve match type and weight while masking reused identifiers and hosts.

### 3.5 Reports, correction and retention

1. A signed-in user can download a redacted JSON report or human-readable Markdown report. Both use the same persisted document and include case assessment, extracted candidates and spans, evidence outcomes/provenance, active and superseded findings, human dispositions, campaign-link states with redacted explanations, rule versions and audit timeline. Source-controlled content is escaped in Markdown; identifiers and source free text remain masked by default.
2. A public correction form accepts a case reference, contact email and explanation without confirming whether the reference exists. It returns a one-time random status token; only its SHA-256 hash is persisted. A requester can check status with both the request reference and token, and invalid credentials receive the same not-found response. Public status checks return a fixed, status-specific message; investigator-authored free-text resolution notes stay in the authenticated investigator queue because masking cannot reliably remove arbitrary names or copied source content. Correction submission is throttled per client address using a scoped HMAC fingerprint in the existing persisted throttle table; raw addresses are not stored.
3. An authorized investigator can apply a correction to a specific extracted entity or evidence item with a required rationale. Entity actions can confirm, reject, or replace a value after deterministic normalization. Evidence actions can set relevance, contradiction, or review-needed status. The action records before/after values, recalculates findings, stales links that lose all shared identifiers, recomputes current-version campaign matches to discover newly supported links, and transactionally enqueues the latest Neo4j projection state.
4. Retention removes expired cases, evidence, associated case audit records and their private uploads, plus expired corpus and correction records. The orphan-file sweep first protects every opaque filename still referenced by surviving upload evidence, so an old file timestamp cannot delete an active case upload. The configured worker runs the purge job.
5. There is no email/SMS notification integration. The requester must retain the one-time status token. Target-specific updates are implemented for investigators; requester-facing delivery/recovery and live Postgres/Neo4j propagation verification remain.

### 4.2 Applied machine-learning and data engineering

1. Used deterministic parsers for structured entities and explicitly labeled claims so the local installation works without paid model access, web search or an LLM.
2. Defined normalization per entity type. URL scheme/host are normalized while case-sensitive paths and query parameters are preserved; IDNA domains are encoded; original forms are retained.
3. Added exact source spans and parser-confidence metadata. Confidence is shown as extraction certainty only, never as a fraud probability.
4. Created a source-adapter contract and a local corpus implementation returning result or no-result observations with provenance. External services and I4C automation are not assumed.
5. Reviewed the official I4C portal pages and MHA material on 21 October 2026. The public pages describe a CAPTCHA-protected citizen search and warn that entries are complaint-based, may be erroneous and are not certified. No public automated API or access authorization was documented in the inspected sources. Recorded the scope, evidence and decision in `SOURCE_ACCESS_REVIEW.md`; no scraping or integration was added.
6. Added a separate optional RDAP domain-metadata adapter only after checking the IANA bootstrap registry and RFC 9224. The adapter downloads/caches the bootstrap document, applies longest suffix matching, accepts only HTTPS registry bases, looks up only extracted domain candidates, disables ambient proxy settings, does not follow redirects, enforces time/response bounds, validates the returned domain, removes contact objects, and stores a response hash plus minimized metadata. 8. Kept registry authority out of machine verdict rules. 9. Implemented deterministic exact-identifier entity matching and versioned campaign scoring; an LLM is not used to merge entities, score campaigns, weigh evidence or decide assessments.
10. Added rule-based claim findings with evidence linkage and history. Empty, failed, unavailable and unchecked outcomes are handled conservatively.
11. Added a time-split-validated scorer for entity extraction, pairwise campaign grouping, claim-level evidence-support precision/recall, adverse-assessment false-positive rate, and latency. Support labels and predictions are compared by case, entity type, and normalized value; the LLM baseline must retain source references for every supported-claim prediction. A deterministic dependency-free TF-IDF/logistic-regression runner trains only on training rows; a provider-neutral LLM/web-search adapter runner, graph-ablation preparation, a four-run comparison validator, and an authorized-data pipeline exporter are implemented. The LLM runner is tested with a synthetic adapter only. Successful worker attempts persist `processing_ms`, measured from the committed processing transition through immediately before the completion commit; queue wait and commit time are excluded. The ablation utility consumes measurements from a real no-graph run and does not simulate an execution. The exporter joins persisted pipeline results to protected pseudonymous labels, HMACs corpus/evidence snapshots, rejects corrected records and human-reviewed campaign links, includes low-signal current-rule candidate groups, and counts active claim-level concerns in its evaluation-only adverse metric. Authorized labels, measured production-pipeline runs, and performance results remain absent; no performance results are claimed.

### 4.3 Security-minded product design

1. Captured consent version and timestamp before processing; enforced consent server-side. Added client-side selection redaction for pasted text; removed spans are replaced before the API request and cannot be extracted. Image/PDF redaction remains a pre-upload user task.
2. Hashed passwords with Argon2, separated roles and bootstrap codes, validated bearer sessions, and audited key access and review paths. API startup requires distinct investigator and reviewer bootstrap codes with at least 32 characters. Failed sign-ins use a generic response for unknown accounts, perform a dummy Argon2 verification, and use database-backed account/address throttling. Registration requests use a separate per-direct-client persistent throttle to slow account creation and one-time setup-code probing. Registration and login throttle keys use HMAC-SHA-256; failure audit records contain no account/address, and expired throttle rows are purged. Forwarded client addresses are not trusted from request headers by the application; proxy deployments must explicitly configure and validate the ASGI server's trusted proxy boundary.
3. Added reviewer-only account listing and activation control. Every status change requires a rationale, is audited without copying the account email into the event detail, increments the target's token version, and prevents self-suspension or removal of the last active reviewer. The responsive reviewer account screen uses the persisted API.
4. Added reviewer-issued password recovery tokens with configurable short expiry, HMAC digest storage, replacement invalidation, one-time consumption, rate-limited failed attempts, audit events, and token-version revocation. Only the raw token is returned once with `Cache-Control: no-store`; the reviewer must deliver it over a separately verified channel. There is no email/SMS delivery or verified-email recovery.
5. Validated file content signatures and sizes; kept uploads private and used opaque storage names. PDF/OCR limits reduce excessive processing.
6. Avoided automatic URL fetching. This prevents the current product from creating SSRF behavior, but also means submitted URLs are not externally fetched or reputation-checked.
7. Restricted analyst and default-report output to minimize free-text exposure: titles, source names/claims/excerpts, review rationales and evidence details are withheld; HTTP(S) source references expose the origin only and redact path/query/fragment values. Authorized investigator/reviewer case views retain source access. Contact identifiers are masked, recruiter claims are hidden, and graph identifiers use stable hashes rather than putting normalized contacts in API node IDs. Evidence graph projection excludes user-authored free text and clears legacy Neo4j properties at sync time; the graph inspector opens the authorized case view for the full record. Analyst audit timelines and report details now retain only an explicit allowlist of metadata, dropping unknown fields instead of trying to detect every possible name or free-text value. This is access-based minimization, not legal anonymization; source hostnames and authorized views may still identify people or organizations.
8. Kept source allegations, observed facts, system matches and human dispositions separate. Reports and UI explain that links and findings are investigative leads and not determinations of guilt.
9. Added correction intake, one-time status credentials, target-specific investigator application and retention. No email/SMS requester notification exists. The privacy notice and retention duration still require approval by the deploying organization; software does not itself guarantee legal compliance.
10. Case detail no longer returns raw background-worker exception strings. It shows safe retry guidance while retaining detailed diagnostics in service logs; a regression test verifies a path, a name and a phone embedded in an internal exception do not reach an analyst response. This only closes the processing-error response path; arbitrary names in evidence content remain a redaction limitation under review.

## 5. Rule and data contracts

### Evidence outcomes

- `result`: a source returned a record; it is not automatically relevant or authoritative.
- `no_result`: the configured source returned no match. It is neutral.
- `unavailable`: source could not be queried.
- `error`: the check failed.
- `not_checked`: no completed check exists.

Every evidence item contains a source name/type, stable reference or local record ID, claim, outcome, excerpt, authority category and retrieval timestamp. Findings snapshot the evidence versions they used. Human relevance and contradiction reviews include reviewer, rationale and time.

### Privacy and correction behavior

Original uploads live in private storage. PostgreSQL controls access to case records. The authorization model is shared-workspace access, not tenant or case ownership isolation: analysts can see all cases in redacted form while investigators/reviewers can inspect originals. Analyst views and downloadable reports mask identifiers; public correction intake does not reveal whether a case exists. Do not place mutually untrusted organizations in one deployment before adding and reviewing tenant isolation. Retention is configurable with `DATA_RETENTION_DAYS`; deletion behavior has been tested in SQLite but requires Postgres verification.

## 6. Local setup and verification commands

1. Install Docker Desktop with its Linux engine and Compose, then copy `.env.example` to `.env`.
2. Replace all example secrets and set distinct investigator and reviewer bootstrap codes. Set a retention period approved by the operator.
3. From the repository root, run `docker compose up --build` and open `http://localhost:5173`. API docs are available at `http://localhost:8000/docs` in this local deployment.
4. Register the first investigator account, then register a separate reviewer account using its one-time code. Submit synthetic or properly authorized material and add traceable records to the local corpus.
5. Backend checks from `backend`: set `$env:PYTHONPATH='.pydeps'`, then run `python -m unittest discover -s tests -v` and `python -m compileall -q app tests evaluation`.
6. Evaluation baseline: from `backend`, provide an authorized time-split JSONL corpus and run `python -m evaluation.baseline_tfidf_logreg <input.jsonl> <output.jsonl>`. Score the output with `python evaluation/evaluate.py <output.jsonl>`. The exact schema and controlled-comparison/ablation commands are in `backend/evaluation/README.md`.
7. Frontend checks from `frontend`: run `pnpm run test:redaction` and `pnpm run build`.
8. Migration check from `backend`: configure a disposable SQLite `DATABASE_URL`, then run `python -m alembic upgrade head` and `python -m alembic check`.
9. Compose syntax from repository root: run `docker compose config --quiet`.
10. Backup from repository root: run `./scripts/backup.ps1 -BackupDirectory <protected-backup-directory>`. Restore using the paired PostgreSQL and upload archives as documented in README. Backups contain personal data and the scripts do not encrypt them.

The latest saved verification results and the exact next implementation steps are in `BUILD_STATUS.md`. A Compose syntax check is not a substitute for a live Postgres/Neo4j integration run.

## 7. Known gaps before production review

- Requester correction status access and target-specific investigator actions exist. Public intake is rate-limited per client address using configurable HMAC-keyed persisted throttles. Email/SMS notification and secure token recovery are absent. Applied corrections recalculate findings, stale invalid links and enqueue graph projection work transactionally. The outbox has SQLite tests but still requires live Postgres/Neo4j concurrency, outage, deletion and rebuild verification.
- Explicit labeled extraction covers company/organization, role/designation/vacancy, recruiter/HR contact, location, dates, amounts, fees, and the supported identifiers. In addition, a narrow deterministic pattern recognizes common hiring constructions such as “We are hiring Data Analysts at Example Ltd” and “Opening for a Data Analyst at Example Ltd”, producing only low-confidence company and role candidates with exact source spans. Other free-form narrative extraction (including recruiter identity and location inference) remains limited pending authorized annotated examples. OCR image-region coordinates are persisted for OCR-derived identifiers, but OCR fixtures still need deployment-container verification.
- Provider-specific access review for any new external sources. RDAP is an optional registration-metadata adapter; no I4C API is implemented or assumed.
- Authorized time-separated labels and real measured comparisons remain pending. TF-IDF/logistic-regression and provider-neutral LLM/web-search baseline runners, full-pipeline export, time-split validation, graph-ablation preparation, metric scoring and matched-run comparison utilities exist. The LLM runner is verified only with a synthetic adapter; the graph-off pipeline must still be run against the same cases and corpus as the full pipeline.
- Additional API authorization/redaction coverage, TLS, stronger CSRF/security hardening, Postgres backup/restore tests and Neo4j outage/rebuild validation. Reviewer-controlled password resets are implemented, but email/SMS delivery and verified-email recovery are absent. Login throttling and reviewer-account locking are covered with SQLite/API tests but need live Postgres concurrency validation.
- Backup/restore scripts with checksum verification exist and pass PowerShell parser checks; a live recovery drill remains pending Docker/PostgreSQL availability.
- Styled PDF reports, remaining coverage for every arbitrary-text output path and source hostname, deployment monitoring and operator runbooks.
- Full end-to-end journey and production-container checks. Do not describe the application as fully working or release-ready until these have been implemented and verified.

### 9.2 Applied machine-learning engineer

### 9.3 Security-minded product designer

1. **Set outcome language and decision boundaries.** Machine assessments use only the conservative evidence labels documented in the product.
